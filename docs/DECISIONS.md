# DECISIONS.md — Architecture Decision Records (ADR)

이 문서는 SB News AI 프로젝트의 주요 기술 결정을 ADR(Architecture Decision Record) 형식으로 기록한다.
형식: **배경 → 선택지 → 결정 → 이유 → 트레이드오프**.

결정은 PROJECT_SPEC §7(기술 스택 제안)과 §21(개발 가정)을 전제로 한다. 모든 결정은
"혼자 개발·운영 가능 / 금융기관 보안심사 통과 가능 / 온프레미스 이전 가능 / 사용자 수십 명 규모"
라는 4대 제약(§7.1)을 최우선 기준으로 삼는다.

---

## ADR-001. 프론트엔드/백엔드 분리 여부

**배경**: §7은 "Next.js Route Handlers 또는 FastAPI, 파이프라인/AI 처리가 무거우면 Python 분리 권장"이라고 제안한다.

**선택지**
- (A) Next.js 단일 저장소 — App Router + Route Handlers를 API로 사용, Worker도 Node.js
- (B) Next.js(프론트) + FastAPI(백엔드/파이프라인) 이원화
- (C) Next.js(프론트) + Python 워커만 분리 (API는 Next.js 유지)

**결정**: **(A) Next.js 단일 저장소(TypeScript) + Node.js 기반 Worker 프로세스**를 채택한다.
Worker는 같은 저장소 안의 별도 실행 진입점(`server/worker`)이며, 별도 언어를 도입하지 않는다.

**이유**
1. 이 프로젝트의 무거운 연산은 "로컬 CPU/ML 연산"이 아니라 "외부 LLM API 호출 대기"다. Python이 유리한 지점(자체 ML 추론, 임베딩 모델 로컬 실행)이 이 프로젝트에는 없다 — 임베딩도 외부 API(§13, AI Gateway)를 통해 받는다.
2. 인턴 1명이 개발하고 다른 사람이 인수인계 받는 구조(§18.3-5)에서, 언어를 하나로 유지하는 것이 유지보수 비용을 크게 낮춘다. TS 하나면 타입을 프론트-백엔드-워커가 공유할 수 있다(DB 스키마 타입, zod 스키마 재사용).
3. Node.js 생태계의 BullMQ(Redis 큐), RSS 파서, cheerio(스크래핑) 등으로 파이프라인 구현에 지장이 없다.
4. `web`과 `worker`는 프로세스로는 분리한다(§15.2 요구사항 — 수집/분석 부하가 사용자 응답을 막지 않도록). 코드 저장소는 하나지만 배포 컨테이너는 둘이다.

**트레이드오프**
- Python 대비 성숙한 NLP/데이터 처리 라이브러리가 적다 → 한국어 형태소 분석기 선택에 제약이 생김(ADR-002에서 별도 처리).
- 향후 정말 무거운 로컬 ML(온프레미스 LLM 서빙 등)이 필요해지면 별도 Python 서비스를 추가해야 할 수 있음. 단, AI Gateway가 provider 인터페이스로 추상화되어 있으므로(§5.3) 이 전환은 애플리케이션 코드 변경 없이 새 provider 어댑터 추가로 해결 가능하다.

## ADR-002. DB 및 검색 전략 — 한국어 형태소 분석 방식

**배경**: PostgreSQL 기본 FTS는 한국어 형태소 분석을 지원하지 않는다. §7.2가 제시한 선택지는 (a) pg_bigm/trigram, (b) 앱 레벨 형태소 분석(mecab-ko, kiwi), (c) OpenSearch + Nori.

**결정**: **MVP는 (a) `pg_bigm`(2-gram 부분일치)로 시작**하고, V1에서 실측 검색 품질이 기준 미달이면 **(b) 앱 레벨 형태소 분석(kiwi, 순수 JS/WASM 바인딩)** 으로 전환한다. (c) OpenSearch+Nori는 운영 부담(별도 클러스터 운영·보안심사 대상 확대)이 이 프로젝트 규모에 비해 과도하므로 V1에서도 채택하지 않고, 사용자 규모가 실제로 수천 명 이상으로 확대되는 시점(§17.1)에 재검토한다.

**이유**
1. `pg_trgm`(3-gram, 표준 contrib)이 아니라 `pg_bigm`(2-gram)을 고른 이유: 한국어/일본어/중국어처럼 짧은 음절 단위 매칭이 잦은 언어는 3-gram보다 2-gram이 재현율이 높다고 알려져 있다(NTT OSS, 다수 한국어 서비스 사례). 별도 확장 설치가 필요하지만 커스텀 Postgres Docker 이미지에서 빌드하면 되고, 순수 오픈소스라 보안심사 부담이 적다.
2. mecab-ko 등 네이티브 바인딩(node-gyp 빌드)은 온프레미스 이전 시 빌드 환경 문제를 일으킬 수 있어 MVP 단계에서는 피하고, WASM 기반 형태소 분석기(kiwi-wasm 등)로 V1에서 전환하는 경로를 열어둔다.
3. OpenSearch+Nori는 검색 품질이 가장 좋지만 "PostgreSQL 하나로 관계형+검색+벡터를 해결"이라는 §7.2 핵심 권고와 충돌하고, 사용자 수십 명 규모에는 명백한 과설계(§18.3-4)다.

**트레이드오프**
- pg_bigm은 형태소 분석기 대비 검색 정확도(특히 어미 변화, 복합어 처리)가 낮다. "저축은행" 검색 시 "저축은행들" "저축은행의" 등은 부분일치로 커버되지만, 동의어 확장("PF" ↔ "프로젝트파이낸싱")은 안 된다 — 이 부분은 F-05의 자연어 검색 프롬프트에서 `keywords` 필드에 동의어 확장을 AI가 미리 넣도록 보완한다(§13.5).
- 검색 전략 전환(pg_bigm → 형태소 분석) 시 재색인이 필요하므로, 인덱싱 로직은 서비스 레이어에서 추상화(`search.service.ts`)해 전환 비용을 낮춘다.

**검증 계획**: V1 착수 전 골든 쿼리 30개로 pg_bigm 검색 품질(정밀도/재현율)을 측정하고, 기준(주관식 기준: 상위 10건 중 관련 기사 7건 이상) 미달 시 전환한다.

## ADR-003. 벡터 검색 방식

**결정**: **pgvector**(PostgreSQL 확장)를 채택한다. 별도 벡터 DB(Pinecone, Weaviate, Qdrant 등)를 도입하지 않는다.

**이유**
1. §7.2 핵심 권고와 일치 — 관계형 데이터(기사 메타)와 벡터(분석 임베딩)를 조인 쿼리 하나로 처리할 수 있어 RAG 후보 축소(F-07의 "필터 → 벡터 검색" 단계)가 단순해진다.
2. 데이터 규모(연 수만 건, §17.1)에서 pgvector의 IVFFlat/HNSW 인덱스 성능은 충분히 검증된 수준이다.
3. 별도 벡터 DB 운영은 인턴 1명 체제에 부담이며, 온프레미스 이전 시 추가 컴포넌트가 하나 더 늘어난다.
4. §20-1 하드 제약에 따라 벡터로 저장하는 것은 원문이 아니라 **AI 생성 분석 텍스트**뿐이므로 저장량 자체가 크지 않다.

**트레이드오프**
- pgvector는 전용 벡터 DB 대비 초대형 규모(수억 벡터)에서는 성능이 떨어진다. 이 프로젝트 규모에서는 해당 없음. 규모가 실제로 임계치에 도달하면 §17.1의 파티셔닝/읽기 복제본 전략과 함께 재평가한다.

## ADR-004. 잡 큐 및 스케줄러

**결정**: **BullMQ(Redis 기반)**를 채택한다.

**이유**
1. ADR-001에서 스택을 Node.js/TypeScript로 통일했으므로 Celery(Python) 대신 BullMQ가 자연스러운 선택.
2. Redis를 캐시와 큐에 겸용해 컴포넌트 수를 줄인다(§7.2 "Redis 캐시+큐+레이트리밋 겸용").
3. BullMQ는 재시도(지수 백오프), 지연 작업(스케줄링), DLQ(실패 큐)를 기본 제공해 §5.2 파이프라인 요구사항(단계별 독립 재시도, 멱등성, DLQ)을 그대로 구현할 수 있다.
4. 파이프라인 각 단계([1] COLLECT ~ [9] PURGE)를 각각 별도 BullMQ 큐/잡으로 등록해 단계별 격리(§5.2)를 보장한다.

**트레이드오프**
- Redis가 단일 장애점이 될 수 있음 → Redis는 AOF 영속화를 켜고, 큐 상태는 최종적으로 DB(`articles.pipeline_stage`, `crawl_logs`)에도 기록해 Redis 데이터 유실 시에도 복구 가능하게 한다.

## ADR-005. 인증 방식

**결정**: **자체 로그인(이메일/비밀번호) + 서버 세션(Redis 세션 스토어) 기반**. JWT는 사용하지 않는다.

**이유**
1. §21-4, §16.1의 명시적 요구사항.
2. 세션은 강제 로그아웃(관리자가 계정 비활성화 시 즉시 접근 차단)과 감사 로그 연계가 JWT보다 쉽다 — JWT는 만료 전까지 서버가 강제로 무효화할 수 없다.
3. 세션 저장소로 Redis를 재사용(ADR-004)해 컴포넌트를 추가하지 않는다.
4. 인증 모듈은 `server/auth/`에 격리하고, `AuthProvider` 인터페이스로 추상화해 향후 SSO(SAML/OIDC/LDAP)를 별도 provider로 추가할 수 있게 한다(§16.1, §21-4).

**트레이드오프**
- 세션 기반은 다중 인스턴스 확장 시 세션 스토어 공유가 필요 — Redis 세션 스토어로 이미 해결됨(무상태 web 인스턴스, §17.1).

## ADR-006. 배포 방식

**결정**: **Docker Compose**(local/staging/production 공통 구성, 환경별 오버라이드 파일 분리). Kubernetes는 지금 도입하지 않는다.

**이유**
1. §7.2, §15.4의 명시적 권고 — 사용자 수십 명 규모에 K8s는 과설계이며 인턴 1명이 운영하기 어렵다.
2. 온프레미스 이전(§15.4, §21-1) 시에도 Docker Compose는 그대로 옮길 수 있다. 관리형 클라우드 전용 서비스(서버리스 DB, 벤더 종속 큐)를 쓰지 않는다는 원칙과 일치.
3. `web`/`worker`/`postgres`/`redis` 4개 컨테이너로 구성이 단순하다(§15.2).

**트레이드오프**
- 향후 사용자가 수천 명 규모로 확대되면(§17.1 "회원 저축은행사 개방") 오케스트레이션 필요성이 커질 수 있음 — 그 시점에 K8s 전환을 재평가한다. 무상태 web/worker 설계(§17.1)로 전환 비용을 낮춰둔다.

## ADR-007. AI Provider 추상화

**배경**: §21-2, §21-3 — Claude API를 우선 지원하되 특정 모델에 종속되지 않아야 한다.

**결정**: `server/ai/gateway.ts`를 단일 진입점으로 하고, `server/ai/providers/`에 provider별 어댑터(`anthropic.provider.ts`, `openai.provider.ts`)를 둔다. 작업 유형(`analyze`/`briefing`/`qa`/`classify`/`nl_search`/`embed`)별로 어떤 provider·model을 쓸지는 DB `ai_models` 테이블에서 관리하며 코드에는 모델명을 하드코딩하지 않는다(§7.3, §21 개발 원칙).

**이유**: §5.3, §20-3 하드 제약(프롬프트 인젝션 방어, 출력 스키마 검증)을 모든 provider 호출 경로에 공통 적용하기 위해 반드시 단일 게이트웨이를 거치게 한다. 이렇게 해야 provider 교체(온프레미스 LLM 포함, §17.2)가 애플리케이션 코드 변경 없이 가능하다.

**트레이드오프**: 게이트웨이 계층이 한 단계 추가되어 최초 구현 비용이 있으나, §18.3-3("나중에 하면 되지로 미루지 마라")에 따라 처음부터 구축한다.

## ADR-008. 모노레포 폴더 구조

**결정**: §10에 정의된 단일 저장소 구조를 그대로 채택하되, Python 워커 분리(ADR-001에서 기각)는 하지 않으므로 `services/worker/`가 아니라 `src/server/worker/`(Node 진입점)로 구성한다.
